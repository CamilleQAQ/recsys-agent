# 2026-11-07 · kuasar_small · Two-Tower + 物品侧特征

## 假设

ID-only 双塔在长尾词表上学不动（61.4% 物品只出现 1 次）。把物品侧的内容特征
（类目、作者频次、上传日期、`is_ad` 等）拼进物品塔，应当让**没见过的物品**也能获得有意义的向量，
从而提升召回——尤其是 Recall@10 这种头部指标。

## 设置

- 数据：`kuasar_small`（2,000 用户 / 454,717 物品 / 758,724 正样本），切分协议与基线完全一致；
  子集特征表由全量按词表切片而来（12 列，子集内 2,055 个广告物品）
- 基线：`two_tower`（ID-only，29,229,888 参数，2026-11-07 重训逐位复现）
- 实验：`two_tower_features`（33,353,589 参数）
  - 物品塔输入 = ID embedding(64) ⊕ 4 × 类目 embedding(16) ⊕ 5 个数值特征
  - 类目：`category_first_code`(38) / `category_second_code`(294) / `item_type_code`(4) / `upload_type_code`(29)，
    编码整体 +1，0 号桶留给缺失
  - 数值：`log1p(author_freq)`、`log1p(caption_tokens)`、`upload_days/365.25`、`is_ad`、`upload_valid`
  - 特征以 buffer 形式挂在模型里 → checkpoint 自带特征，推理只需 `item_id`
- 其余超参与基线相同：batch 2048、Adam 1e-2、20 epochs、in-batch 负采样、`mask_false_negatives=false`

## 结果（测试集，4,275 个目标）

| 指标 | ID-only 基线 | + 物品特征 | 变化 |
| --- | --- | --- | --- |
| Recall@10 | 0.001600 | **0.003200** | **+100.0%** |
| NDCG@10 | 0.001202 | 0.002465 | +105.1% |
| HitRate@10 | 0.003500 | 0.006000 | +71.4% |
| Recall@20 | 0.003475 | **0.004408** | **+26.9%** |
| NDCG@20 | 0.001839 | 0.002836 | +54.2% |
| HitRate@20 | 0.008500 | 0.008500 | 0 |
| Coverage | 0.071592 | 0.071134 | −0.6% |

验证集 best epoch 19：Recall@20 = 0.004133（基线 0.003542），但 Recall@10 = 0.001467（基线 0.001858）。

## 解读

1. **头部指标提升明显**：Recall@10 翻倍、NDCG@20 +54%，说明内容特征确实让「冷门物品」变得可召回；
   Recall@20 只涨 27%，因为尾部本来就有更多候选，特征带来的边际收益递减。
2. **验证/测试结论不完全一致**：验证集只有 5,775 个目标，Recall@10 在验证上反而下降。
   这是小样本噪声（单目标权重约 1.7e-4），不能据此否定特征的作用，但也说明**需要多 seed 复核**。
3. **Coverage 基本不变**：特征没有让推荐更集中，说明提升不是「更频繁推热门」换来的。
4. **参数量 +14%，checkpoint +20 MB**：代价可接受；全量 4M 物品时特征 buffer 约 208 MB，需要重新评估。

## 已知问题

- 单 seed、单切分；验证/测试指标方向不一致，结论强度有限；
- 用户侧特征（活跃度）没有接入——子集来自 processed 存储，不含 `user_features.csv` 切片；
- 用户塔仍是纯 ID，用户冷启动没有改善。

## 下一步

- 多 seed（3 个）复跑，确认 Recall@10 的翻倍不是偶然；
- 用户活跃度入塔（需要在子集构建时切 `user_features.csv`）；
- 超参扫描（dim / batch / lr）补齐工作清单第 5 项；
- 全量阶段：特征 buffer 的内存与构建成本要单独估算。
