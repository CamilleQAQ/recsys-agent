# 2026-11-07 · kuasar_small · MIND（多兴趣召回）

## 目标

给系统加**第二路召回**：MIND 用胶囊网络 + 动态路由把用户历史压成 K 个兴趣向量，
服务时对每个候选取 ``max over K`` 个兴趣的相似度。它与双塔的差别在于「一个用户不是一个向量」，
理论上更适合兴趣多峰的短视频场景。

## 为什么用 torch-rechub

MIND 的参考实现在 TorchEasyRec 里，但它的依赖（`fbgemm-gpu` / `torchrec`）只有
`manylinux` 的 cp310–312 wheel，Windows + Python 3.14 装不上。

`torch-rechub`（datawhalechina，MIT）是纯 PyTorch 实现，`pip install torch-rechub` 即可：

- 30+ 模型（MIND / DSSM / SASRec / DIN / DCNv2 / MMOE…），后续可继续接入；
- 我们的做法：**只借模型本体**，数据、训练循环、评测仍走本项目契约；
- 版本钉 `1.0.0`，源码 sparse-checkout 到 `third_party/torch-rechub`（commit `7ea1731`）作审计。

## 设置

- 数据：`kuasar_small`（2,000 用户 / 454,717 物品 / train 748,674），请求级切分与之前一致
- 样本：每个「用户 + 位置」一条 (历史, 下一个物品)，共 **746,674 条/epoch**
- 模型：`embed_dim=64`、`max_length=20`、`interest_num=4`、`temperature=0.1`
- 训练：in-batch softmax，Adam lr=1e-2，batch=1024，20 epochs（CPU 4 线程约 60 分钟）
- 评测：历史 = train（验证）/ train+val（测试），分数取 K 个兴趣的最大值

## 结果（测试集，4,275 个目标）

| 指标 | 双塔 + 物品特征 | **MIND** | 变化 |
| --- | --- | --- | --- |
| Recall@10 | 0.003200 | **0.003742** | +16.9% |
| Recall@20 | 0.004408 | **0.005675** | **+28.8%** |
| HitRate@20 | 0.008500 | **0.010500** | +23.5% |
| NDCG@20 | 0.002836 | 0.002712 | −4.4% |
| Coverage | 0.071134 | 0.070765 | −0.5% |

验证集（epoch 20）：Recall@20 = **0.007650**，且最后三轮仍在上升（0.00496 → 0.00765）——**没有收敛**。

## 解读

1. **MIND 作为第二路召回是成立的**：Recall@20 +28.8%、HitRate@20 +23.5%，
   说明多兴趣向量确实捞到了双塔漏掉的候选；Coverage 不变，不是靠更集中地推热门。
2. **NDCG@20 略低**：召回阶段的排序质量由后续精排负责，这里可以接受；
   但如果直接把多路结果合并做最终排序，需要加权或交给排序模型。
3. **训练预算对 MIND 极其敏感**：8 epochs 的版本测试 Recall@20 只有 0.002183，
   20 epochs 到 0.005675（2.6 倍）。MIND 的胶囊路由参数更多、收敛更慢，
   这与双塔（8 轮就能到 0.002）形成对比——值得写进实验记录。
4. **未收敛**是下一步最明确的提升点：把 epochs 提到 30–40，或加学习率衰减。

## 已知问题

- 单 seed；
- 20 epochs 未收敛，当前数字不是 MIND 的上限；
- 用户侧特征（活跃度）没有接入；
- 训练耗时约 60 分钟（CPU），比双塔（18 分钟）贵 3 倍，多路召回的总预算要算进来。

## 下一步

- MIND 训练到收敛（30–40 epochs），确认上限；
- 双塔 + MIND 两路召回融合（加权/去重），看融合后 Recall@20 是否 ≥ 两路各自最优；
- 排序阶段接 LightGBM / DIN（`kuasar_ranking` 样本已就绪）。
