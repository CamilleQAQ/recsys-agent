# 给 DeepSeek 的开发任务：跑通 `kuasar_small` 离线推荐 MVP

在当前仓库实现并实际运行一条离线链路：**Two-Tower + MIND 召回 → 双路融合 → LightGBM 排序 → 简单类目重排 → 统一评估**。目标是让链路可执行、可复查、可作为后续 Research Agent 的评测工具。验收看接口、数据口径和复现结果，各层的指标允许持平或退化。

开始前读 `PROJECT_MASTER.md` 的 Phase 5、8、9、11，`PROJECT_PROGRESS.md` 的最新记录，以及 `docs/data-contract.md`。先核对现有召回适配器、`kuasar_ranking.py`、`kuasar_subset.py`、`LightGBMRankerAdapter` 和统一指标。改动限于本任务需要的桥接、编排、校验和报告，保留已有调用入口。

## 1. 范围与 CPU 预算

- 仅 `kuasar_small`，显式传数据集参数，避免走默认的 `kuasar`。使用已有数据和工件，不重建数据子集，不下载新数据，不运行全量训练或全量评测。允许只读 mmap 父数据集已有排序工件来提取子集样本，禁止从原始 CSV 重建全量排序数据。
- 固定 `artifacts/kuasar_small/two_tower_features.pt` 和 `artifacts/kuasar_small/mind20.pt`。核对 SHA256、数据切分指纹、ID 映射摘要和词表规模。**双塔与 MIND 训练预算均为 0**，不改权重、不扫参、不做多 seed。MIND 路由种子固定为 `1234`，固定评测用户顺序与批配置。
- **CPU 单进程串行，计算线程最多 4，常驻内存上限 4 GiB。** 在导入计算库前限制 OpenMP/BLAS 线程，并设置 PyTorch 和 LightGBM 的线程数。监测峰值 RSS。数据映射、特征和候选按批处理，复用已有分批 Top-K，避免生成全用户 × 全物品的分数矩阵。
- **实跑墙钟预算合计 45 分钟**，覆盖冒烟、取样、排序训练、验证/测试和复验，编码时间另计。LightGBM 最多 **1 次正式训练、50 轮、100,000 条训练候选、10 分钟**，随机种子 `42`。先做小规模冒烟并记录耗时。正式运行应有超时控制并分阶段落盘。缺依赖、超时或超内存时保存已完成产物并报告停点，不自动重跑或加预算。依赖只需核对现有 `requirements/optional-lightgbm.txt`，不装其他模型栈。
- 本轮不接 LightGCN、DIN、DCNv2、TIGER、Agent、RAG 或在线服务，不修改 `third_party/`，不覆盖已有 checkpoint 和实验目录。

## 2. 实施步骤

### A. 固定数据与评测口径

核对当前子集为 2,000 用户、454,717 物品，train/validation/test 为 748,674 / 5,775 / 4,275 条正样本，采用 `per_user_last_two_requests`。复用 `PreparedData`、`seen_items_for_split`、现有目标聚合和指标函数。两条召回通道使用相同的用户集合、候选词表、历史曝光过滤和 K。MIND 验证历史为 train，测试历史为 train + validation。评估目标只用于计算指标，不强行插入候选，也不参与融合、打分或重排。口径或工件不匹配时先停下来记录差异。

### B. 召回与融合

1. 分别通过现有适配器取 Two-Tower 和 MIND 的精确 Top-100。每个数据切分只计算一次各通道的结果，供所有对照复用。候选保留内部 `user_idx`、`item_idx`、来源通道及各来源名次，供输出时还原原始 ID。若现有接口只返回 ID，首版只记录可取得的名次，不伪造原始分数。
2. 以双塔为起点，按各通道原始名次轮流取一个尚未入池的候选，去重后最多保留 100 个。某一路耗尽就由另一路补齐，结果保留该物品在两路中所有可查的来源与名次。不比较或相加两路原始分数。记录重复数、补位数和候选不足的用户数。
3. 在同样的最终候选预算下，对比双塔 Top-100、MIND Top-100、融合 Top-100。记录 Recall@100、Coverage、两路候选重叠、各自独有的目标命中和融合丢掉的目标命中。独有命中按实际 `(user_idx, item_idx)` 目标对计数，不用总体 Recall 差值反推。

### C. LightGBM 排序

1. **训练只取已有曝光排序工件的 train 分区。** 从父数据集 `data/kuasar/processed/ranking/` 只读 mmap 对应数组，通过原始 ID 对齐父、子 user/item 词表。仅保留子集用户和可映射物品。按原请求保留候选边界，过滤后重新计算 group 长度。按固定 seed 在可用请求中抽取完整请求，最多 100,000 行，不能在请求中间截断。用原点击标签训练，仅采纳仍同时包含正负候选的请求，并记录过滤前后请求数、行数和正负数。校验每个 group 的长度、用户和行对齐。不得用 val/test 标签、未知曝光或召回未命中来补训练负例。
2. 复用 `LightGBMRankerAdapter` 的 **LambdaRank** 路径。首版只用子集 `ItemFeatures` 的物品元数据，如类目、物品类型、上传类型、标题 token 数和广告标记。固定特征列序、缺失值处理和 dtype，保存进模型旁的配置。训练与融合候选打分共用同一特征构造逻辑。把曝光样本与召回候选的分布差异记进报告。
3. 对同一份融合 Top-100 候选打分，按排序分数降序，分数相同时沿用融合名次。保存 Booster，验证新进程重载后对同一特征样本的分数一致。LambdaRank 输出用于相对排序，主报告用 Top-K 指标。若另报曝光候选上的请求级 NDCG，单独列出评估集和分组口径。

### D. 简单重排与系统评估

1. 从 LightGBM 排序列表依次选取 Top-20，已知一级类目首遍最多取 5 个。首遍凑不足 20 个时，按原排序补齐剩余候选，记录放宽次数。缺失类目不计入已知类目配额。任何步骤均不得引入候选池外物品、历史已曝光物品或重复物品。若合法候选不足，返回实际数量并记录原因。
2. 用相同用户和目标，对比 **双塔 Top-20、融合后 Top-20、融合 + LightGBM Top-20、再加重排的 Top-20**，报告 Recall@20、HitRate@20、NDCG@20 和 Coverage。排序与重排使用同一融合候选池。另报告重排前后每用户已知一级类目数的均值、未知类目占比、补位次数，以及各阶段耗时、总耗时和峰值内存。
3. 用验证集完成接线和口径核查。参数和规则固定后跑测试集，分别保存两套指标。不要根据测试结果调融合比例、类目配额或排序参数。当前测试切分已有历史结果，报告定位为 MVP 验证。

## 3. 交付物

- **一个可直接运行的离线入口**，支持固定配置、指定验证或测试切分、选择工件目录和重用召回缓存。写清从仓库根目录运行的 PowerShell 命令。配置至少包含数据集、两份 checkpoint、种子、候选预算、类目配额、特征列、线程数和超时。
- 在 `artifacts/kuasar_small/` 的独立子目录保存 LightGBM 模型、特征契约、候选缓存和结果样例。缓存绑定数据指纹、checkpoint SHA256、切分、路由种子和候选 K，不兼容时明确拒绝复用。候选样例应能看出原始用户/物品 ID、各召回来源、融合名次、排序分数及最终名次。
- 在 `experiments/YYYY-MM-DD-kuasar_small-recsys-mvp/` 保存 `config.toml`、`metrics.json`、`checkpoint.txt`、`report.md`。记录精确命令、数据与模型指纹、训练样本量、各阶段对照、实际耗时、峰值 RSS、降级情况和已知限制。大缓存与权重留在 `artifacts/`。
- 更新 `PROJECT_PROGRESS.md`，链接本轮产物并标明「`kuasar_small` 离线 MVP」的验收状态。全量、MIND 重训和 Agent 保留为后续事项。

## 4. 验收标准

1. 从现有两份召回 checkpoint 和子集数据出发，实际完成融合、LightGBM 训练/保存/加载、重排，生成验证及测试 Top-K。LightGBM 必须实际参与打分，缺依赖时标记排序未完成。
2. 自动核查候选无重复、无历史曝光泄漏、来源和 ID 可追溯、融合候选不超过 100、最终不超过 20。排序和重排的物品都属于同一个融合池。训练只读取 train 标签，训练/推理特征名称和列序一致。
3. 用已保存的模型和同一份验证召回缓存复跑下游，核对 Top-K 和指标一致，复验无需重训。至少对固定配置的召回结果抽查可复现性，记录所用用户顺序和批配置。报告包含同候选预算对照、各层指标与资源成本。
4. 记录运行 `python -B scripts/zoo.py check`、`python -B scripts/check_project.py`、`python -B scripts/smoke_adapters.py` 的实际结果。若有历史警告或失败，区分原有问题与本次回归。
5. 完工回复逐条列出通过、失败或未跑，以及对应证据路径。若达到预算上限，交付已完成阶段的产物、停止原因、复现命令和可继续的入口，缺失阶段留待办。
